# Архитектура

Обычное Spring MVC приложение. Зависимости направлены от веб-слоя к сервису,
репозиторию и модели данных.

| Пакет         | Ответственность                                              |
|---------------|--------------------------------------------------------------|
| `web`         | Контроллеры, HTML-формы, подписи для интерфейса, HTTP-ошибки |
| `service`     | Операции с полкой, проверка владельца, транзакции            |
| `service.dto` | Команды и результаты операций, не зависящие от HTTP и JPA    |
| `repository`  | Запросы к БД через Spring Data JPA                           |
| `domain`      | JPA-сущность и перечисления                                  |
| `config`      | Настройки Spring Security и OAuth-клиента                    |

Контроллеры передают сервису идентификатор владельца и команду, получают DTO.
JPA-сущности в шаблоны не передаются. Сервис не знает об HTML-формах,
HTTP-статусах и OIDC. Исключение `ItemNotFoundException` преобразуется в 404
в `WebExceptionHandler`. Зависимости проверяются ArchUnit.

## Авторизация и данные

Вход: OAuth 2.0 Authorization Code + OpenID Connect, PKCE S256, state и nonce.
Spring Security проверяет ID token и создаёт серверную сессию. Выход завершает
сеанс приложения и Keycloak. Идентификатор владельца состоит из issuer и subject;
имя и email для этого не используются.

Все запросы к записи ограничены владельцем. Формы изменения данных используют
POST и CSRF-токен; пользовательский текст экранируется Thymeleaf. Структуру БД
создаёт Flyway, Hibernate проверяет её соответствие модели.

## Развёртывание

Локальный стенд использует PostgreSQL и Keycloak в Docker; порты привязаны к loopback.
Keycloak работает в режиме разработки. Для итогового задания отдельно настраиваются
Ubuntu VM, WireGuard и HTTPS с проверкой отсутствия доступа без VPN.

При смене адресов нужно согласовать `APP_BASE_URL`, `OIDC_ISSUER_URI`, redirect URI
и post-logout URI клиента Keycloak. При HTTPS — установить `COOKIE_SECURE=true`.
